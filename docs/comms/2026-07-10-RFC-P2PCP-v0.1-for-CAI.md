## 2. Mission and non-negotiables  [✓ AGREED — captain's rulings, LOCKED]
P2PCP exists so that **anybody** can transact compute for AI models without data
centres or monopoly rent — this is TernOO's reason-to-adopt beyond hobbyists, and it
shapes everything:

1. **Public and trustless. Strangers are the point.** Global consensus among
   mutually-distrusting strangers with no coordinator is not a cost we accept — it is
   the product we are buying.
2. **ONE mode.** No trusted tier, no friends/LAN mode, no development mode that ships.
   A trusted variant that exists anywhere is a permanent downgrade-attack backdoor;
   the backdoor that is never built never needs nailing shut.
3. **P2PCP is a protocol, not a TernOO component.** Hardware/OS/application agnostic.
   Specified completely enough to write on a roll of loo paper and hand to a stranger,
   who can then implement a conforming node on anything. TernOO is the **reference
   implementation**, not the owner. The spec is the kept original; implementations are
   projections.
4. **No Ethereum import.** No EVM, no Solidity, no gas market. Vibe-coding tokenomics
   in Solidity would import the entire speculation slope (MEV, gas, token culture) —
   the exact premature consolidation this project exists to refuse.
5. Existing sovereignty invariants hold: the network arrives as **one narrow,
   auditable organ** (the allow-list's first citizen), never a promiscuous surface.

## 3. Problem class — what we ARE and are NOT building  [✓ AGREED]
We are building a **permissionless distributed ledger with Byzantine consensus among
strangers** — the problem class colloquially called "blockchain." We are NOT assuming
Bitcoin's silhouette (linear chain of blocks, global total order, world-computer).
The industry consolidated "distributed consensus" into "the blockchain" in 2009 the way
it consolidated programming into text syntax in 1975; we return to the pre-consolidation
problem (Byzantine agreement, Lamport 1982) and design our member of the family for
**this cargo**. The cargo is narrow: the only things strangers must globally agree on
are **credit balances** (no double-spend of earned CompuToken) and **burn records**
(identity weight). Compute receipts are pairwise events that touch consensus only when
they move the ledger. The right structure (chain / DAG / block-lattice / committee) is
§11-Q1, not an assumption.

Node anatomy (all implementations): **daemon** (host app: socket, keys, ledger state,
gossip, scheduler) → **contract machine** (component, §5) → **worker adapters**
(llama.cpp, the 5500FP emulator, anything — the bonsai_runner pattern) → **harness
seam** (a local model's harness discovers remote compute by asking its own daemon;
the model itself never knows, exactly as GHOST's none→consent→delegate works today).

## 5. The one normative machine  [✓ AGREED principle · ⚠ DELIBERATE scope]
Verification-by-replay requires every node to replay a contract **identically** —
determinism cannot be an implementation choice. Therefore the spec contains exactly one
normative machine: the **TernOO Contract Machine (TCM)** — a tiny, fully-specified,
deterministic VM over the 24-trit word grammar (a minimal subset of the 5500FP model),
implementable in a few hundred lines on any platform. Ethereum's one good idea (the
shared machine) at loo-paper scale, minus the baggage. Other implementations never host
a TTree or become TernOO — they only interpret contract words for verification, the way
every torrent client implements SHA-1 without becoming git. TernOO runs contracts
natively at full speed (home ISA); everyone else interprets and gets the same bits —
the golden law exported as a treaty. Everything else we have (content store, TTree/
OTree, GristMill-as-ledger-face, native words on the wire) is **non-normative reference-
implementation advantage**, listed in an appendix, binding on no one.
⚠ Open: how minimal is TCM v0.1 — receipts/transfers/burn only, or general job
contracts from day one? (§11-Q4.)

## 6. Economics and identity  [✓ AGREED core · ⚠ DELIBERATE bootstrap]
The token never "becomes" computation — it is the meter, not the electricity. A distant
daemon spawns a worker because its policy accepted a paid job; the ledger records the
transfer; burn fires per CompuToken rules. Since credit is earned by cycles and burned
on use, the only way to buy compute is to have contributed compute — the currency is a
memory of work done, with no accumulation surface to speculate on.
**Identity = unforgeable costliness:** with no gatekeeper, identity must cost something
scarce; **provably-burned compute** is the native candidate for Sybil resistance —
burn isn't only anti-speculation, it can be the identity weight itself.
⚠ Open: the bootstrap problem — genesis nodes have nothing to burn (§11-Q3).

## 7. Consensus — the open heart  [⚠ DELIBERATE — primary ask]
The graveyard of "useful-work" chains is one problem: verifying work trustlessly costs
as much as redoing it. TernOO's religion — deterministic, bit-exact, law-tested,
replayable execution over content-addressed programs — is precisely the property that
problem needs, and the property mainstream GPU/float stacks cannot promise.
**The thesis, stated for the spec's cover: not "cheap compute" — "compute you can
verify."** Verification family we propose: spot-replay of deterministic TCM contracts +
redundant quorum sampling for statistical jobs (inference) + stake-in-burned-CompuToken
with slashing. The intern we wired this week (speculative decoding: the boss verifies k
drafted tokens in one cheap pass) is the verification economics in miniature.
What remains genuinely open is the **ledger consensus structure** — see §11-Q1.

## 8. Cryptography doctrine  [✓ AGREED doctrine · ⚠ DELIBERATE interim]
**Novel composition, gauntlet-tested primitives.** Designing our own protocol and
consensus: legitimate, necessary. Deploying home-rolled primitives (hashes, signatures)
against adversaries before hostile review: the classic graveyard. Consequences:
- The **CRYPTO primary** gets its first inhabitants: signature words, digest words,
  receipt words, challenge/nonce words — the wire format is self-describing TernOO
  words, but every structure is specified so any platform can emit/verify them.
- `KNOWN.md`'s caveat (ternary_sponge: accident-resistance and local tamper-evidence
  YES, **remote-adversarial NO until external cryptanalysis**) is hereby **promoted to
  critical path**. The external-gauntlet arc (the DM-consultation pattern from the MMID
  saga) is the road to ternary-native primitives.
- ⚠ Open: until the gauntlet is passed, may v0.1 use established binary primitives
  (e.g. ed25519 signatures, SHA-class digests) as an explicitly-marked interim
  projection — the spec naming the ternary-native forms as the kept-original
  destination? (§11-Q5 — this is a keep-the-original doctrine question, your turf.)

## 9. Threat model  [✓ AGREED list — additions welcome]
The flip: a local sovereign system had little to hide; a public mesh has everything to
**verify**. Targets are integrity, not secrecy: forged receipts · fabricated results ·
Sybil swarms · eclipse attacks (isolating a node behind lying peers) · resource
exhaustion / spam jobs (the room check generalizes to admission policy) · replay of
stale receipts · malicious contracts (TCM must be resource-bounded — no Turing tarpit)
· downgrade pressure toward any weaker mode (structurally impossible: no weaker mode
exists, §2.2). Verify-don't-trust is already the house religion (verify-on-fetch,
golden tests, gates, refuse-when-unsure); the machinery must now be built for strangers.
