TernOO-5500FP

A self-describing word architecture for the 5500FP balanced ternary processor.

Overview

TernOO-5500FP is an experimental computer architecture built for the 5500FP balanced ternary processor. Instead of treating a machine word as anonymous storage that only gains meaning after extra interpretation, TernOO treats each 24-trit word as something that already carries its own role and structure. [file:1]

In this design, a word can represent executable behaviour, a data value, a coordinate in space, a stream endpoint, or part of a neural or visual structure, depending on the fields encoded inside it. The white paper describes this as a 2-trit primary field, a 4-trit qualifier field, and an 18-trit payload, all packed into a single self-describing word. [file:1]

The core idea is simple: move more meaning into the machine word itself, so less of the system depends on external lookup tables, translation layers, or separate representations of the same thing. [file:1]

What makes it different

Most modern systems draw hard boundaries between code, data, objects, interfaces, and diagrams. TernOO-5500FP explores what happens when those boundaries are softened at the word level, so the same underlying structure can be read as executable behaviour, program state, geometric position, or a visual symbol. [file:1]

The white paper defines nine primary type slots, with current emphasis on EXEC, MAP, DATA, NEURAL, and I/O. It also introduces mechanisms such as Double Null for user-defined meta-constructs, PIGART for rendering directly from word structures, and GristMill as a proposed content-addressed component model built around MAP-word coordinates. [file:1]

Self-describing words

Each word carries its own category and semantics in its bit-pattern equivalent, rather than relying on separate metadata structures. [file:1]

Objects as native words

The USER-DEF pointer/object form is described as a compact launch descriptor containing code, data, and cursor information in one word. [file:1]

Visual structure

MAP words and renderer opcodes allow geometry and program structure to share the same underlying representation. [file:1]

Room to grow

The draft keeps some primary slots open or reserved so the architecture can extend without abandoning the original layout. [file:1]

Why ternary

TernOO-5500FP is built around balanced ternary, where each digit can take one of three values: negative, zero, or positive. The white paper argues that this is not just a historical curiosity but a mathematically elegant base for representation, especially when a system wants compact symmetry, signed values, and naturally three-way distinctions. [file:1]

The 5500FP substrate itself is a 24-trit balanced ternary processor, and the draft uses that structure directly rather than translating ternary ideas back into binary conventions. The paper also points to recent work on ternary-quantised neural models as a separate sign that three-valued representation can be efficient in practice, though TernOO’s own neural ideas remain architectural work in progress. [file:1]

Visual programming

One of the most distinctive ideas in the project is that diagrams should not merely document a program after the fact. In the TernOO model, the same words that define a program can also be rendered as points, lines, symbols, and connections, so the visual form and the executable form are two views of one structure. [file:1]

This is where FlowCode and PIGART come in. The paper describes FlowCode as a visual environment in which flowchart symbols, spreadsheet-like formulas, and interface components can map directly to TernOO words, while PIGART provides renderer opcodes that draw from those same words rather than from a separate design file or compiled intermediate form. [file:1]

  • Process symbols can correspond to object words. [file:1]
  • Connection arrows can correspond to executable call relationships. [file:1]
  • Position can be encoded through MAP words. [file:1]
  • The display and the program can therefore share one source structure. [file:1]

Current status

The current public implementation is a Python emulator, described in the white paper as version 0.3. It includes a CPU model for 24-trit arithmetic and execution, word constructor functions, decoding and inspection tools, segment helpers, Double Null support, a first-stage PIGART renderer, an interactive REPL, and test coverage for the main architecture elements. [file:1]

The paper says the emulator runs with Python 3.12 and no external dependencies, and it lists passing tests for primary types, word constructors, arithmetic, rendering, and neural word construction. It also presents the emulator as scaffolding for a longer path toward native execution on 5500FP hardware rather than as the final destination of the project. [file:1]

Implemented now

Core word encoding, decoding, constructor functions, emulator execution loop, segment helpers, Double Null support, renderer primitives, REPL tooling, and tests. [file:1]

Still ahead

Native execution workflow, later rendering backends, fuller neural inference, and wider system pieces such as the more developed GristMill and GHOST concepts. [file:1]

Next steps

The roadmap described in the draft moves from emulator validation to a FlowCode environment, then to an assembly bridge, then to native execution on 5500FP hardware, and eventually to a self-hosting visual system where programs can be constructed and modified directly through the same word structures they run on. [file:1]

Some of the later concepts, especially GHOST and the fuller GristMill storage model, should be read as exploratory architecture rather than finished software. The value of the project today is that the core word model and its supporting emulator already give those larger ideas a concrete base to grow from. [file:1]
